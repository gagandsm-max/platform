# Platform Device Pack Contract Foundation

**Scope:** contract, deterministic packaging, static validation, and fictional fixtures only.
**Mother Reference:** Platform v3.2.2.
**Runtime/device certification:** not included.

## 1. What a Device Pack is

A Device Pack is the Platform-owned, versioned extension unit that can declare how a supported device or resource family is identified and how supported protocol observations map into Platform canonical semantics. The Mother Reference allows Device Packs to join identification, discovery, SNMP/MIB, REST/API, gNMI/YANG, CLI/NCM, inventory, topology, normalized metrics, alert/RCA semantics, dashboards, compatibility and provenance.

This checkpoint deliberately implements only the common contract surface needed before vendor-specific content exists:

- pack identity and version;
- deterministic device matching metadata;
- capability declarations;
- protocol requirements and security posture;
- external reference/dependency declarations;
- declarative normalization metadata;
- provenance/certification metadata;
- bounded, dependency-free static validation;
- fictional validation fixtures.

## 2. What a Device Pack is not

A Device Pack is not:

- a Credential Profile or secret store;
- an authorization grant;
- a polling policy or Monitoring Profile;
- a place to encode customer thresholds or polling intervals;
- an executable plugin;
- a shell/JavaScript/Python execution container;
- a mechanism for silently enabling legacy protocols;
- proof that a real vendor/model/firmware combination has been certified.

A Device Pack declaring compatibility is **NOT** proof of real-device certification. Real compatibility requires protocol/device integration evidence and the applicable certification process.

## 3. Authority boundaries

The contract follows these Mother Reference boundaries:

- Core remains the authority for Device Pack metadata, selection, policy, provisioning and authorization.
- Sensors will consume approved Device Pack runtime mappings in a later checkpoint; this repository foundation does not implement Sensor loading.
- Credential Profiles own credential secret values. Packs may declare only a credential-profile **type** where useful.
- Monitoring Profiles/policies own polling, adaptive polling, thresholds, validation and assignment behavior.
- Platform security policy always wins over pack declarations.
- Legacy/insecure protocols remain disabled by default, explicitly enabled by authorized policy and audited. A pack can declare compatibility; it cannot enable the protocol.
- Device Pack signing, trust-store format and runtime Device Pack API-level numbering are required future work. Their exact contract is **TBD — Decision Required** and is not invented here.

## 4. Repository layout

This lane uses:

```text
device-packs/
  README.md
  schema/
    manifest.schema.json
  examples/
    minimal/manifest.json
    multi-protocol/manifest.json
  fixtures/
    cases.json
  tools/
    validate.mjs
```

A future distributable Device Pack archive uses a deterministic logical root:

```text
manifest.json                 # required
references/                   # optional declarative external artifacts
fixtures/                     # optional non-secret test evidence
```

The manifest is the only required file in this checkpoint. References are package-relative when bundled. Absolute paths, `..` traversal and backslash-based filesystem escape forms are rejected. Validation performs no external network fetch.

Signing/envelope files are intentionally not specified until the Mother Reference signing/trust decision is made.

## 5. Manifest versioning

`schemaVersion` versions the Platform-owned manifest contract. This checkpoint defines `1.0.0`.

`packId` is a stable lower-case Platform identifier. `packVersion` uses SemVer 2.0 shape. A deployable validation set may contain only one manifest for a given `packId`; multiple competing versions must not be silently selected.

Breaking manifest-contract changes require a new major `schemaVersion`. Runtime Core/Sensor Device Pack API-level compatibility is separate and remains **TBD — Decision Required**.

## 6. Certification and provenance

Mother Reference certification classes are represented exactly as:

- `OFFICIAL_CERTIFIED`
- `PARTNER_VERIFIED`
- `CUSTOMER_CUSTOM`
- `EXPERIMENTAL`

These are declarations/metadata, not evidence generated by this validator. The validator never upgrades certification status.

Publisher types are `PLATFORM`, `PARTNER` and `CUSTOMER`. Provenance entries preserve source class, source reference and redistribution posture. Customer-supplied material must not be assumed redistributable.

A broader publication lifecycle state machine beyond these certification classes is **TBD — Decision Required** and is intentionally absent.

## 7. Supported-device matching semantics

Matching consumes observed/provisioning identity evidence. It does not fabricate vendor, model, software or firmware facts.

Allowed selector fields are:

- `vendor`
- `family`
- `product`
- `model`
- `platform`
- `software`
- `firmware`
- `api`
- `mib`

Each rule has a unique integer `priority`; lower values have stronger precedence. Equal priority inside one pack is rejected because it creates avoidable ambiguity.

Each condition explicitly declares `operator`:

- `EXACT` — literal comparison;
- `GLOB` — bounded wildcard syntax using only `*` and `?`; regular-expression syntax is not supported.

`caseSensitive` is mandatory so comparison semantics are never guessed.

When a future runtime evaluates multiple packs, rule rank is:

1. lowest `priority`;
2. highest count of `EXACT` conditions;
3. highest total condition count.

If more than one matched candidate still has identical rank, the outcome is **AMBIGUOUS**. There is no arbitrary winner.

Required runtime outcomes are:

- `MATCH`
- `NO_MATCH`
- `UNKNOWN` when required observed identity is missing/insufficient
- `AMBIGUOUS` when equal-strength candidates remain

This checkpoint validates rule definitions only; it does not perform live discovery or device matching.

## 8. Protocol declarations

The contract admits protocol families already present in the Mother Reference:

`ICMP`, `SNMP`, `SNMP_TRAP`, `SYSLOG`, `SSH_CLI`, `TELNET`, `NETCONF`, `REST`, `RESTCONF`, `GNMI`, `GRPC`, `FLOW`, `DNS`, `HTTP`, `HTTPS`, `TLS`, `REDFISH`, `WINRM`, `CLOUD_API`, `OTLP`, `SCP`, `SFTP`, `TFTP`, `FTP`.

A declaration records:

- `REQUIRED` or `OPTIONAL` compatibility;
- whether the mode is legacy/insecure;
- optional port suggestion (1-65535), never a hard-coded customer constraint;
- bounded transport/security-mode metadata;
- optional Credential Profile **type**, never an ID/value/secret;
- prerequisite capability references.

`TELNET`, `TFTP` and `FTP` must be marked `legacy: true` and may not be declared `REQUIRED` by this foundation. Secure policy remains authoritative for all protocol enablement.

Ports in packs are suggestions only. Mother Reference defaults/examples do not become immutable runtime ports.

## 9. Capability declarations

Capabilities are declarative Platform semantic identifiers. They describe what the pack says it can support; they do not authorize the user or guarantee runtime/device compatibility.

Capability IDs are unique within a pack and may reference required protocol families. Protocol declarations may in turn reference prerequisite capabilities. Static validation checks those references and duplicate declarations.

## 10. Normalization contract

Normalization is declarative. Each mapping contains:

- canonical observation/metric `key`;
- source protocol;
- source field/OID/path identifier as metadata;
- optional declared reference ID;
- value type;
- optional unit;
- target entity/component metadata;
- provenance reference;
- `qualityFallback`, which this foundation permits only as `UNKNOWN`;
- optional deterministic transform metadata.

Only deterministic transforms are admitted:

- `IDENTITY`
- `SCALE` with a finite numeric factor
- `OFFSET` with a finite numeric offset

No arbitrary expressions, shell commands, JavaScript, Python or executable code are allowed in a Device Pack.

This foundation does **not** define a production metric catalogue, vendor OIDs, gNMI paths, REST paths or CLI parsers.

## 11. References and dependencies

`references` declare external/bundled MIB, YANG, OpenAPI or model artifacts by logical ID, version/provenance metadata and optional package-relative path. The validator checks declaration integrity and path safety; it does not download anything.

`dependencies` use exact `packId` + `packVersion` references in this foundation. Range-resolution semantics are **TBD — Decision Required**. When validating a pack set, every dependency must be present and exact, and dependency cycles are rejected.

## 12. Security boundary

Validation fails closed for:

- password/community/token/private-key/cookie/reusable-secret fields;
- Credential Profile IDs or embedded credential values;
- credentials embedded in URLs;
- bearer/token query-string material;
- PEM private-key material;
- script/shell/command/exec/code fields;
- absolute filesystem paths;
- `..` path traversal or encoded traversal markers;
- malformed/unknown top-level and nested fields;
- malformed versions/IDs;
- duplicate pack IDs, capabilities, references, provenance IDs or normalization keys;
- unknown protocol enums;
- equal-priority pack-local match rules;
- unresolved dependencies/references;
- dependency cycles;
- unsafe/unbounded manifest strings and arrays.

The validator never performs an external network fetch and never evaluates embedded code.

## 13. Static validator

Default fixture-suite validation:

```bash
node device-packs/tools/validate.mjs
```

Validate one or more manifests/directories:

```bash
node device-packs/tools/validate.mjs device-packs/examples/minimal device-packs/examples/multi-protocol
```

The validator uses only Node.js standard-library modules. It is Platform semantic validation, not a claim that a generic JSON Schema engine was executed.

`schema/manifest.schema.json` documents the structural contract. The Node validator separately enforces Platform semantic/security rules.

## 14. Fixture policy

`fixtures/cases.json` is entirely fictional and non-production. It covers valid minimal/multi-protocol/legacy/multiple-rule packs and invalid duplicate identity, malformed version, unknown protocol, duplicate capability, ambiguous priority, secret fields, traversal, executable content, invalid normalization keys, missing identity, unresolved references/dependencies, dependency cycles, strict unknown fields and bounded-size failures.

No fixture contains a real customer address, credential, OID, CLI command, REST path, gNMI path or real vendor compatibility claim.

## 15. Relationship to Monitoring Profiles

A Device Pack declares compatibility, capabilities and mappings. A Monitoring Profile/policy decides how monitoring is applied: metric selection, polling/adaptive polling, assignment/inheritance, thresholds, validation and alerts. The contract deliberately contains no polling interval or threshold defaults.

## 16. Relationship to Credential Profiles

Credential Profiles are encrypted, tenant/scoped Platform state with separate `USE`, `EDIT` and `REVEAL` authorization. Device Packs never contain secret values and do not grant authorization. A protocol declaration may state only the compatible Credential Profile type.

## 17. Relationship to Device Pack Studio

Device Pack Studio is the future UI/publishing workflow for identification rules, mappings, compatibility, provenance, testing and publication. This checkpoint provides the common source contract and static validator only. It does not implement Studio UI, MIB/API/YANG parsing, sample-device testing or publishing.

## 18. Vendor certification boundary

Static validity means only that a manifest conforms to Platform contract/security rules. It does not prove:

- an OID exists on a vendor device;
- an API/gNMI/NETCONF path is supported;
- a CLI parser/command works;
- a firmware/model combination is compatible;
- a monitoring metric is semantically correct;
- a Device Pack is production-ready.

Real certification requires protocol/device integration evidence, test-lab fixtures/evidence, security review and applicable release gates.

## 19. Future work explicitly excluded

Later checkpoints must separately implement or decide:

- signed-pack envelope, trust roots and signature verification;
- runtime Device Pack API level and Core/Sensor compatibility matrix;
- Device Pack Studio;
- MIB/API/YANG/CLI parser pipelines;
- runtime Core persistence and Sensor loading;
- discovery/provisioning integration;
- canary/rollback orchestration;
- marketplace/download/update services;
- vendor-specific packs and certification evidence.
